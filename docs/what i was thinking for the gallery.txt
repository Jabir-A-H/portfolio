### Option 1: Framer Motion `layoutId` Shared-Layout Glider (Recommended)

#### How it works:
Every project row has an allocated right-side "dock" in the negative space. Whichever row is currently active (via scroll focal point or hover) renders the visual preview frame wrapped in `<motion.div layoutId="gallery-viewfinder">`. 

When the active project changes from Row 1 to Row 2, Framer Motion automatically performs a **FLIP animation** (First, Last, Invert, Play) on the compositor thread: it calculates the delta between Row 1's position and Row 2's position and animates the frame smoothly gliding down to the new row.

* **Why do it (Benefits):**
  - **Zero Manual Coordinate Math:** No fragile `offsetTop`, `window.scrollY`, or manual pixel measuring. Framer Motion handles the exact viewport calculation automatically, even on window resize or dynamic content shifts.
  - **Natural Scroll Travel:** While you are within a project's 350px height, the frame scrolls with the page naturally because it is physically rendered within that active row's DOM tree.
  - **Buttery Smooth Handoff:** Gliding between rows uses hardware-accelerated transforms (`transform: translate3d`).
* **Why not do it (Risks & Failure Modes):**
  - **Rapid Flick-Scroll Lag:** If a user scrolls aggressively at high velocity through all 6 projects in half a second, the `layoutId` transition has to cancel and retarget multiple times rapidly, which can cause slight visual catch-up lag on low-powered mobile devices if the spring damping is too stiff.

---

### Option 2: Absolute Y-Axis Spring Coordinate Bus (`useSpring` Y-Tracking)

#### How it works:
The project list container is `position: relative`. A single `<motion.div>` preview card is positioned `position: absolute; right: 0; top: 0;`. 

We measure the active row's `offsetTop` and the scroll progress within that row (`0.0` to `1.0`). We feed `targetY = activeRow.offsetTop + (scrollProgress * driftAmount)` into a continuous spring: `y = useSpring(targetY, { stiffness: 220, damping: 28 })`.

* **Why do it (Benefits):**
  - **Continuous Micro-Parallax:** Enables exact control over how the image moves *while* you scroll within that 350px window (e.g. drifting down 40px as you scroll through the row, before snapping to the next row).
  - **Decoupled from DOM hierarchy:** The preview is a single DOM node that never unmounts or re-parents.
* **Why not do it (Risks & Failure Modes):**
  - **Resize & Font-Load Desync:** If images or custom fonts load late and push layout heights, cached `offsetTop` values become stale, requiring a `ResizeObserver` on the container to recalibrate coordinates.
  - **Sub-pixel Jitter:** Calculating `offsetTop` plus scroll deltas on every tick can cause minor sub-pixel rendering blur on standard-DPI screens if `will-change: transform` isn't applied.

---

### Option 3: Scoped Sticky Segments (Pure CSS Sticky per Row)

#### How it works:
Each project row is wrapped in a container that defines its active height (e.g., 350px–450px). The preview card sits inside that container with `position: sticky; top: 25vh;`. 

Because CSS `sticky` elements are confined to their parent container, the preview naturally stays at `top: 25vh` while you scroll through that project, and as soon as that project's container ends, it naturally scrolls up and off with the row as the next project's sticky card enters.

* **Why do it (Benefits):**
  - **Pure CSS Native:** 0 lines of animation JavaScript. Zero main-thread load, works even with JS completely disabled.
  - **Perfect Scroll Anchoring:** The browser compositor handles the anchoring natively.
* **Why not do it (Risks & Failure Modes):**
  - **No Gliding Between Rows on Hover:** Because each card is locked to its own HTML container, the card **cannot** float or glide across containers when you hover a different row. It can only crossfade in and out.
  - **Duplicate DOM Nodes:** Requires rendering a preview container for every single project row rather than sharing one traveling frame.


#### How it works architecturally:
1. **The Outer Frame (`layoutId="viewfinder"`):**  
   Governs the **macro position**. When switching from Project 1 to Project 2 (via scroll boundary crossing or hover), this outer frame glides down between the rows using hardware-accelerated spring physics.
2. **The Inner Parallax Layer (`useScroll` + `useTransform`):**  
   Governs the **micro motion**. We hook into Framer Motion's `useScroll({ target: activeRowRef })`:
   ```tsx
   const { scrollYProgress } = useScroll({
     target: rowRef,
     offset: ["start end", "end start"]
   });

   // Smoothly drifts from -25px to +25px as the row scrolls through the viewport
   const parallaxY = useTransform(scrollYProgress, [0, 1], [-25, 25]);
   ```
   The image inside the viewfinder gently drifts along the Y-axis as you scroll naturally through the row.

#### Why this hybrid is the ultimate solution:
* You get the **best of both worlds**:
  * **Zero fragile math** for positioning the frame between rows (Framer's `layoutId` handles all row height changes and screen resizes automatically).
  * **Tactile, fluid parallax** while scrolling through any project's vertical space.
* And on desktop, hovering instantly glides the entire assembly to that row, where it immediately responds to scroll again.
